# 2026-09-30：连接池、分片、流式与缓冲升级

功能阶段 5、6、7、8、10、11 已接入，公开调用仍返回 net::task；net/co2 未修改。
本轮测量支持保留默认系统分配器、每调用 Arena 和单分片 client。可选缓存减少分配成本，但小消息 p99 没有稳定收益。
64 B/64 在飞仍有回退，跨 executor 的两分片入口成本明显更高，不能宣布完整性能验收通过。
接口和限制见 [升级说明](../../docs/runtime-upgrade.md)。

## 测量与来源

GCC 13.3、C++14、Release -O3 -DNDEBUG、epoll、回环 TCP/TCP_NODELAY，接收窗口 65536 B、64 streams。
protobuf 3.21.12；net 7dff859、co2 a265e57。i7-13700KF、Linux 7.0.0-34，powersave/balance_performance，turbo 开启，CPU 未独占。
client/channel 在 CPU 2 的同一执行器上运行调用方和服务端，使用一条连接；runtime 由 CPU 2 的外部 caller 驱动，
两个 client/server actor 运行在 CPU 4/6，两条连接、三个线程。后者测量整套拓扑，不能当作单纯 facade 开销或多核扩展比。
测量期间没有本项目并行编译、测试或分配插桩诊断。

`upgrade_suite.py` 每配置五轮、预热 3000、正式 30000 请求；隔轮反转配置和版本顺序。
每轮 CSV 独立重算计数、时间戳和 p99；首轮和参数瘦身后的终轮各 170 次运行、510 万请求，全部零错误且 eligible。
两组完整结果都保留。表中的 p99 是逐轮中位数；配对变化是同轮新/旧比值的中位数，两者不必相等。

基线为本阶段开始前冻结的 1–4 步二进制 `build/runtime-baseline/steps-1-4-unary-bench`；
仅有该中间二进制和哈希，没有对应中间源码归档，不能声称可由当前源码重建。
当前二进制、源码（包含 runtime/message）、依赖及构建信息随环境快照保存。
原始 CSV.gz/环境/汇总位于 `build/bench-results/steps5-11{,-compact}/`；
[可保留数据](2026-09-30-upgrade.json) 包含两轮摘要、来源、诊断与测试日志。

## 默认路径回归

新增 channel 的排队/重试选项扩大了 call_options；默认 client 协程现只捕获实际使用的 deadline/timeout/metadata，
减少每调用申请字节，保持公开 API 和相对超时的起算位置。该调整没有消除高并发回退，不能把前后两次运行差异全部归因于它。

| --- | --- | --- | --- | --- | --- | --- |
| bytes | 64 | 1 | 4.592 | 4.640 | +1.0% | 235402 |
| bytes | 64 | 64 | 55.300 | 58.325 | +5.5% | 997658 |
| protobuf | 64 | 1 | 4.767 | 4.772 | +1.4% | 225087 |
| protobuf | 64 | 8 | 11.212 | 11.628 | +2.6% | 698537 |
| protobuf | 4096 | 1 | 5.786 | 5.846 | +1.5% | 186922 |
| protobuf | 4096 | 8 | 16.797 | 17.666 | +3.6% | 457332 |

bytes64/n64 当前五轮 p99 为 57.772–93.097 µs，异常尾轮没有删去；基线为 55.161–56.408 µs。
首轮该项中位数 55.533→59.254 µs；参数瘦身后仍有约 5.5% 配对回退，尚未完成后续归因。
这些短闭环轮次不替代之前仍未通过的加长开放负载及跨进程验收，也没有重新证明与裸 net 的开销门槛。

## 缓存与申请量

同拓扑的缓存配对结果如下。最终组的 bytes4KiB/n8 recycling p99 中位数改善约 3.2%，但吞吐约低 5.2%；
小消息的两种缓存均未稳定改善 p99，默认保持关闭。

| 配置 | system/每调用 Arena p99 µs | recycling/cache64 p99 µs |
| --- | --- | --- |
| bytes64/n1 | 4.622 | 4.635 |
| bytes64/n8 | 10.042 | 10.009 |
| bytes4096/n1 | 5.486 | 5.676 |
| bytes4096/n8 | 16.489 | 15.969 |
| protobuf64/n1 | 4.805 | 4.818 |
| protobuf64/n8 | 11.505 | 11.552 |
| protobuf4096/n1 | 5.879 | 5.818 |
| protobuf4096/n8 | 19.062 | 18.106 |

另用全局 new/new[] 插桩，每种配置预热 1000、正式 5000，全部成功。bytes64/n8 的 system 为每调用 7 次 new，
recycling 为 2 次；protobuf64/n8 的 per-call/cache64 均为 11 次，但完整分配追踪分别为 **5493/3397 B 每调用**，
申请字节减少约 38.2%，没有丢失栈条目。Arena 缓存另冷持有 64 份 2 KiB 初始块及对象，满额拒绝，并非减少所有负载下的驻留内存。
这些数值包含公共驱动、不包含直接 malloc、对齐分配或 RSS；插桩延迟不参加性能结论。
因此保留有界 Arena 缓存作为显式配置，不能据此宣称 p99 优化已通过。

重新运行无网络 API 原型：owned direct awaiter 由历史 144 B 增到 **192 B**；当前 co2 内联区亦为 192 B，
该原型测得 A task 与 B direct 都是每调用 1 次 new。原型仍不含完整 RPC 生命周期；历史 B=0 的计数不能沿用。
此结果不改变用户已经选择保留 task 的接口决定。

## 入口成本

| 在飞 | client p99 µs / 成功每秒 | channel p99 µs / 成功每秒 | runtime p99 µs / 成功每秒 |
| --- | --- | --- | --- |
| 1 | 4.675 / 234616 | 5.107 / 211250 | 58.382 / 40117 |
| 8 | 9.935 / 806916 | 12.850 / 593357 | 21.547 / 402803 |

channel 增加池选择、准入和治理生命周期；runtime 还跨线程投递并唤醒执行器。
这些机制解释了可能的成本来源，但本轮没有内核调度采样，不能据数字断言具体停顿来自哪条线程、Wi-Fi 或代理。
低 p99 的关键业务应优先在所属分片上调用；外部 facade 的吞吐/尾延迟以及真正多连接多核扩展仍需专项测量。
本轮尚未对 owned streaming、receive_source 和压缩做端到端性能对照，仅验证其功能、容量和生命周期。

## 正确性验证

最终 Debug 30/30，protobuf Release 和 ASan/UBSan/LSan 各 40/40，TSan 28/28；epoll/poll/select/io_uring 均执行，无跳过。
流式测试覆盖大消息分片、窗口耗尽后的释放、空消息/半关闭、方法 ID 复用、跨线程取消、关闭后跨 context 晚释放、
zstd/LZ4 两算法与 receive_source 两路径。混合生成服务覆盖四种方法及跨分片 metadata 往返。
失败 handler 和非法 OK 说明只结束当前流；零响应 client-streaming 成功 END 与重复 SETTINGS 有确定性拒绝回归。
线程启动失败在 Release 和 ASan 都有注入；ASan 下成功创建委托其 interceptor，不绕过线程登记。
TSan 排除全局 new 故障注入、pthread_create 拦截并关闭 protobuf；发行版 protobuf 库本身未插桩。
wire libFuzzer 配合 ASan/UBSan 10 万轮通过，max_len=4096；该沙箱 fuzz 运行关闭 LSan，独立完整测试已开启 LSan。
CSV 校验器五项测试通过。依赖的 [net 冷定时器 OOM 限制](../../docs/net-timer-oom.md) 保留。
