# 2026-09-27：开放负载瓶颈修复与验收复测

**接收路径的瓶颈已修复，严格开放负载验收仍未通过。** 新增独立的固定接收窗口，避免协议帧上限同时限制一次读取量。
4 KiB 的成功请求 p99 与拒绝次数明显下降；优化窗口的开放负载仍为 **0/20 轮有效**。
保留 300k/s、128 个驱动槽、64 个 RPC stream、100 µs 最大发起迟到及零错误/零丢弃门槛，没有删除失败轮次。
完整逐轮结果、环境、诊断、源码与样本哈希见 [JSON 快照](2026-09-27-open-load.json)。
后续已确认一类长停顿包含非自愿抢占和运行队列等待，见[调度诊断补充](2026-09-27-scheduler.md)；本报告保留当时的原始结果。

P0 基准将协议帧上限设为 8192 B，原接收窗口随之只有 8208 B；一个稳定态 4 KiB REQUEST 占 4121 B，两个请求便放不下。
读链因此频繁补读、搬移半帧，而 raw net 已使用 65536 B 窗口。本轮在保持协议帧上限、池预算和 stream 上限不变的条件下，
让 RPC 也可配置 65536 B 窗口。`connection_options.receive_buffer_bytes` 默认仍为 `0`，沿用 `max_frame_size + 16`，
显式值须在 `[max_frame_size + 16, 16 MiB + 16]` 内。每连接一次分配；基准从 8208 增至 65536 B，额外占用 57328 B。
服务端窗口总量受 `max_connections` 限制，关闭但尚未析构的连接仍占名额，分配失败回滚名额。net 未修改。

单独的 `strace` 闭环对照中，双方均完成 1000 次预热和 10000 次正式 4 KiB 调用、64 个在飞：
`recvfrom` 从 **22353 降至 2076，减少 90.7%**；两组均含 350 次 EAGAIN，`sendmsg` 均为 1687 次。
计数包括启动与预热，受跟踪干扰的耗时不参与延迟验收。

正式开放负载使用同一个未插桩 Release 二进制，交替比较 8208/65536 B 窗口，并保留 raw 对照。
epoll、系统帧分配器、单条回环 TCP、TCP_NODELAY；同线程固定 CPU 2，跨进程客户端 CPU 2、服务端 CPU 4。
仍是 i7-13700KF、GCC 13.3、`-O3 -DNDEBUG`，net `7dff859`、co2 `a265e57`；主机未独占，powersave/balance_performance、turbo 开启。
采样期间未并行运行本项目的编译和测试。每配置 5 轮，每轮预热 5000 次、计划 600000 次；隔轮反转顺序。
60 轮共计划 36000000 次，实际发起 35969196 次，成功 35935149 次，拒绝 34047 次，驱动丢弃 30804 次，超时及其它错误均为 0。
