# 2026-09-27：P0 成本归因与可靠性验证

本轮完成分配栈归因、可选发送队列探针、跨进程基准与可靠性测试，并修复准入分配失败遗留方法槽的问题。
未引入调用对象池、时间轮或调度优化。net 保持不变，其冷定时器堆 OOM 会终止进程，详见文末限制。

正式测量采用未插桩 Release、系统帧分配器、epoll、单条回环 TCP、`TCP_NODELAY`，环境与首轮相同：
i7-13700KF、Linux 7.0.0-34、GCC 13.3、C++14、`-O3 -DNDEBUG`，net `7dff859`、co2 `a265e57`。
同线程双方固定 CPU 2；跨进程客户端 CPU 2、服务端 CPU 4，分别运行一个执行器线程，两者为不同物理核。
机器未独占，`powersave` / `balance_performance`、turbo 开启。正式运行期间未并行编译或运行其它本项目测试。

每种拓扑 8 种配置、各 5 轮，每轮预热 5,000 次、正式计划 600,000 次，共 4,800 万次正式计划请求。
其中 34,008 次被发生器丢弃，实际进入调用 API 的次数为 47,965,992。
连接、握手和首次方法定义排除在正式区间外；成功响应逐字节核验，脚本独立重算每轮 CSV 的计数、时间顺序和分位数。

这不是一次单变量优化前后对照；相对首轮的分位数变化不能直接归因到代码变更。net 无 RPC 准入、取消、截止语义，

开放负载固定每秒 300,000 次、128 个驱动槽、64 个 RPC stream，每轮计划发起区间约 2 秒。
有效门槛仍为全部成功、无发生器丢弃、每次实际发起相对计划迟到不超过 100 µs。
**两种拓扑的开放负载均为 0/20 轮有效**；每一轮都超过迟到门槛，部分还发生拒绝或驱动丢弃。

分配追踪使用独立 `diagnose` 构建，64 B、预热 1,000 次、正式 5,000 次，保留完整符号栈。

六轮均无丢失、无未分类项，最长实际栈 13 帧，未触及 24 帧上限；追踪总数与正式区间分配计数相符。

可靠性验证结果：

- Debug、Release、ASan/UBSan/LSan 各 15/15，独立 TSan 14/14；四种网络后端均实际执行，无跳过。
  TSan 不构建与其全局 new 拦截冲突的故障注入程序；net 源码一起插桩。
- 每个后端的压力测试运行 32 波、2,048 次调用，外部线程并行请求取消，混合截止和关闭；检查只完成一次及最终资源归零。
  确定顺序测试另覆盖完成后取消、待处理 END 与取消竞争、关闭优先、截止优先、取消与截止同时满足的优先级。
- 部分写取消验证 `REQUEST(1) → CANCEL(1) → REQUEST(2)` 的完整字节流、缓冲保活及迟到 END 不覆盖已完成调用缓冲。
  容量测试覆盖两连接的请求/响应/控制、活跃调用额度与慢读端占额，以及客户端 pending、请求池和方法槽限制。
- 故障注入验证 4 个准入失败点及恢复、2 个同步任务启动失败点、7 个握手/读写协程帧失败点。
  回归复现了方法容量为 1 时，A 准入分配失败后 B 被永久拒绝的问题；修复回滚本次新增方法槽后，四个准入失败点均可恢复 B 调用。
- 最终基准程序在同线程与跨进程各通过 13 个 sanitizer 自检场景，覆盖正常、驱动丢弃、拒绝与超时，并验证服务端关闭排空。

已知限制：net `timer_heap::push` 在 `noexcept` 内扩容，冷定时器堆的分配失败会 `std::terminate`。
独立最小复现实际以 SIGABRT 退出，gdb 确认调用路径；按用户选择未修改依赖。
默认故障测试不覆盖此处 OOM，也不覆盖内部 `run_async` 完成状态的全部普通分配失败；不能宣称任意 OOM 可恢复。
复现和后续修复边界见 [net 定时器 OOM 说明](../../docs/net-timer-oom.md)。
